## 1. PagedAttention

### 1.1 背景与动机

#### 传统 KV Cache 的问题

在 Transformer 自回归解码中，每个 token 需要存储 Key 和 Value 用于后续 attention 计算：

$$\text{KV Cache Size} = 2 \times L \times H \times D \times S \times B \times \text{dtype\_size}$$

其中：
- $L$: 层数（如 LLaMA-7B 有 32 层）
- $H$: 注意力头数（如 32 个头）
- $D$: 头维度（如 128）
- $S$: 序列长度（如 2048）
- $B$: 批大小（如 32）
- dtype_size: 数据类型字节数（FP16 为 2 字节）

**示例计算**：LLaMA-7B 在 batch=32, seq=2048 时：
```
KV Cache = 2 × 32 × 32 × 128 × 2048 × 32 × 2 bytes
         = 34,359,738,368 bytes
         ≈ 32 GB
```

**核心问题**：
1. **内存浪费**：预分配最大序列长度，实际使用率低
   - 平均序列长度 << 最大长度
   - 内存浪费 60-80%
2. **内存碎片**：不同请求长度不同，难以复用
3. **批大小受限**：内存限制导致无法增大批次
4. **无法动态调整**：静态分配无法适应动态负载

#### 虚拟内存的启发

操作系统的虚拟内存机制提供了解决思路：
- **分页 (Paging)**：将内存分成固定大小的页
- **按需分配**：只分配实际使用的页
- **页表映射**：虚拟地址 → 物理地址
- **共享内存**：多进程共享相同物理页

### 1.2 PagedAttention 原理

#### 核心设计

PagedAttention 将 KV Cache 组织为固定大小的**物理块 (Physical Block)**：

```
┌─────────────────────────────────────────┐
│  Physical Memory (GPU VRAM)             │
├─────────────────────────────────────────┤
│  Block 0: [K₀, V₀] (16 tokens)         │
│  Block 1: [K₁, V₁] (16 tokens)         │
│  Block 2: [K₂, V₂] (16 tokens)         │
│  ...                                    │
│  Block N: [Kₙ, Vₙ] (16 tokens)         │
└─────────────────────────────────────────┘
```

每个序列维护一个**块表 (Block Table)**，记录逻辑块到物理块的映射：

```
Sequence 1: [Logical 0 → Physical 3]
            [Logical 1 → Physical 7]
            [Logical 2 → Physical 12]

Sequence 2: [Logical 0 → Physical 1]
            [Logical 1 → Physical 5]
```

#### 关键组件

**1. KVBlock - 物理块**
```python
class KVBlock:
    block_id: int           # 物理块 ID
    ref_count: int          # 引用计数（Copy-on-Write）
    num_tokens: int         # 当前存储的 token 数
    k_cache: np.ndarray     # Key cache [block_size, num_heads, head_dim]
    v_cache: np.ndarray     # Value cache [block_size, num_heads, head_dim]
```

**2. BlockTable - 块表**
```python
class BlockTable:
    block_ids: List[int]    # 逻辑块 → 物理块映射
    
    def get_physical_block(self, logical_idx: int) -> int:
        return self.block_ids[logical_idx]
```

**3. BlockAllocator - 块分配器**
```python
class BlockAllocator:
    free_blocks: List[int]  # 空闲块池
    blocks: Dict[int, KVBlock]
    
    def allocate() -> KVBlock:
        """分配一个空闲块"""
    
    def free(block_id: int):
        """释放块到空闲池"""
    
    def fork(block_id: int) -> int:
        """Copy-on-Write 复制"""
```

### 1.3 Copy-on-Write 优化

在 beam search 或并行采样中，多个序列共享相同前缀：

```
Prompt: "What is the capital of"
├─ Beam 1: "... France? Paris"
├─ Beam 2: "... France? The capital is Paris"
└─ Beam 3: "... France? It's Paris"
```

**传统方法**：每个 beam 复制完整 KV Cache
**Copy-on-Write**：共享前缀块，只在修改时复制

```python
# Fork 序列
seq2 = kv_cache.fork_sequence(seq1)

# 共享前缀块（引用计数 +1）
block_table[seq2] = block_table[seq1].copy()
for block_id in block_table[seq2]:
    blocks[block_id].ref_count += 1

# 写入新 token 时才复制
def append_token(seq_id, k, v):
    last_block = get_last_block(seq_id)
    if last_block.ref_count > 1:
        # Copy-on-Write
        new_block = allocate()
        copy_data(last_block, new_block)
        last_block.ref_count -= 1
        block_table[seq_id][-1] = new_block.block_id
    
    new_block.append(k, v)
```

### 1.4 内存效率分析

#### 内存占用对比

| 方法 | 内存占用 | 说明 |
|------|----------|------|
| 传统预分配 | $2LHD \times S_{\max} \times B$ | 按最大长度分配 |
| PagedAttention | $2LHD \times \lceil S_{\text{avg}} / B_s \rceil \times B_s \times B$ | 按实际长度分配 |

其中 $B_s$ 是块大小（如 16），$S_{\text{avg}}$ 是平均序列长度。

**示例**：
- 最大长度 2048，平均长度 512
- 传统方法：2048 tokens/seq
- PagedAttention：512 tokens/seq
- **内存节省**：75%

#### 块大小选择

块大小 $B_s$ 的权衡：
- **太小**（如 4）：块表开销大，管理复杂
- **太大**（如 128）：内部碎片多，浪费内存
- **推荐**：16-32 tokens

**内部碎片率**：
$$\text{Fragmentation} = \frac{B_s - (S \bmod B_s)}{B_s}$$

平均碎片率约为 $B_s / 2$。

## 2. Continuous Batching

### 2.1 背景与动机

#### 静态批处理的问题

传统静态批处理 (Static Batching) 的工作流程：

```
Batch 1: [Seq A (50 tokens), Seq B (100 tokens), Seq C (200 tokens)]
         ↓
         等待所有序列完成 (200 steps)
         ↓
Batch 2: [Seq D, Seq E, Seq F]
```

**核心问题**：
1. **GPU 空闲**：短序列完成后，GPU 仍在等待长序列
   - Seq A 在 50 步后完成，但要等到 200 步
   - GPU 利用率：50-60%
2. **延迟增加**：新请求必须等待当前批次完成
   - 队头阻塞 (Head-of-Line Blocking)
3. **吞吐量受限**：批大小固定，无法动态调整

#### 性能分析

假设批次中序列长度分布：
- Seq A: 50 tokens (25%)
- Seq B: 100 tokens (50%)  
- Seq C: 200 tokens (100%)

**GPU 利用率**：
```
Steps 1-50:   3 sequences active → 100% utilization
Steps 51-100: 2 sequences active → 67% utilization
Steps 101-200: 1 sequence active → 33% utilization

Average: (50×100% + 50×67% + 100×33%) / 200 = 58.5%
```

### 2.2 Continuous Batching 原理

#### 核心思想

**迭代级调度 (Iteration-Level Scheduling)**：每个解码步骤后重新调度批次。

```
Step 1: [A, B, C]           (3 active)
Step 2: [A, B, C]           (3 active)
...
Step 50: [A✓, B, C] → [B, C, D]  (A完成，D加入)
Step 51: [B, C, D]          (3 active)
...
Step 100: [B✓, C, D] → [C, D, E] (B完成，E加入)
```

**关键特性**：
- 完成序列立即移出
- 新请求立即加入
- 保持批次满载
- GPU 利用率 >90%

#### 调度器设计

**1. 请求队列 (Request Queue)**
```python
class RequestQueue:
    def __init__(self, policy: SchedulingPolicy):
        self.policy = policy  # FCFS, SJF, Priority
        self._queue = []
    
    def add(self, request: Request):
        """添加请求到队列"""
        if self.policy == SchedulingPolicy.FCFS:
            self._queue.append(request)
        elif self.policy == SchedulingPolicy.SJF:
            # 按预估长度排序
            self._queue.append(request)
            self._queue.sort(key=lambda r: r.estimated_length)
        elif self.policy == SchedulingPolicy.PRIORITY:
            # 按优先级排序
            heapq.heappush(self._queue, (-request.priority, request))
```

**2. 批次调度器 (Batch Scheduler)**
```python
class BatchScheduler:
    def schedule(self) -> SchedulerOutput:
        """每步调度决策"""
        # 1. 移除完成的序列
        self._remove_finished()
        
        # 2. 从队列中选择新请求
        while self._can_add_request():
            request = self.queue.pop()
            self.running.append(request)
        
        # 3. 区分 prefill 和 decode
        prefill_requests = [r for r in self.running if r.is_prefill]
        decode_requests = [r for r in self.running if not r.is_prefill]
        
        return SchedulerOutput(
            prefill_requests=prefill_requests,
            decode_requests=decode_requests,
            num_batched_tokens=self._count_tokens()
        )
```

### 2.3 调度策略

#### FCFS (First-Come-First-Served)

**特点**：
- 按到达顺序服务
- 公平性最好
- 可能导致队头阻塞

**适用场景**：
- 公平性要求高
- 请求长度分布均匀

#### SJF (Shortest Job First)

**特点**：
- 优先处理短请求
- 平均延迟最低
- 长请求可能饥饿

**适用场景**：
- 延迟敏感应用
- 短请求占多数

**平均延迟分析**：
假设请求长度 $L_1 < L_2 < ... < L_n$

FCFS 平均延迟：
$$\bar{T}_{\text{FCFS}} = \frac{1}{n} \sum_{i=1}^{n} \sum_{j=1}^{i} L_j$$

SJF 平均延迟：
$$\bar{T}_{\text{SJF}} = \frac{1}{n} \sum_{i=1}^{n} (n-i+1) L_i$$

SJF 总是优于 FCFS：$\bar{T}_{\text{SJF}} \leq \bar{T}_{\text{FCFS}}$

#### Priority Scheduling

**特点**：
- 支持差异化服务
- 可设置优先级
- 需要防止饥饿

**优先级计算**：
```python
priority = base_priority + urgency_factor - wait_time_penalty

# 防止饥饿：等待时间越长，优先级越高
wait_time_penalty = -0.1 * wait_time_seconds
```

### 2.4 Prefill 和 Decode 混合批处理

#### 挑战

Prefill 和 Decode 的计算特性不同：
- **Prefill**: 处理整个 prompt，compute-bound
- **Decode**: 生成单个 token，memory-bound

混合批处理需要平衡两者：

```
Batch: [Prefill(512 tokens), Decode(1 token), Decode(1 token), ...]
       ↓
       Prefill 主导计算时间
```

#### 解决方案

**1. Chunked Prefill**
将长 prompt 分块处理：
```python
def chunked_prefill(prompt_tokens, chunk_size=512):
    for i in range(0, len(prompt_tokens), chunk_size):
        chunk = prompt_tokens[i:i+chunk_size]
        process_chunk(chunk)
```

**2. 分离调度**
```python
# 优先处理 decode（低延迟）
if num_decode_requests > 0:
    process_decode_batch()

# 然后处理 prefill（高吞吐）
if num_prefill_requests > 0 and gpu_has_capacity():
    process_prefill_batch()
```

def reorder_requests(requests):

## 3. Speculative Decoding

### 3.1 背景与动机

#### 自回归解码的瓶颈

Transformer 自回归解码的特点：
```python
for i in range(max_length):
    # 每步只生成 1 个 token
    logits = model(input_ids)  # 加载全部权重
    next_token = sample(logits)
    input_ids.append(next_token)
```

**核心问题**：
1. **Memory-Bound**：每步加载完整模型权重
   - LLaMA-7B: 14GB 权重
   - 带宽限制：~1.5 TB/s (A100)
   - 计算利用率：<10%
2. **串行生成**：无法并行化
3. **延迟线性增长**：$T = N \times t_{\text{step}}$

#### 计算分析

**理论峰值 vs 实际性能**：
- A100 FP16 峰值：312 TFLOPS
- 自回归解码实际：~20 TFLOPS
- **利用率**：6.4%

**原因**：内存带宽瓶颈
```
Time per token = Model_size / Memory_bandwidth
                = 14 GB / 1.5 TB/s
                ≈ 9.3 ms
```

### 3.2 Speculative Decoding 原理

#### 核心思想

使用**小模型推测 + 大模型验证**：

```
Draft Model (小):  快速生成 k 个候选 token
                   ↓
Target Model (大): 一次前向验证所有候选
                   ↓
Rejection Sampling: 接受/拒绝候选，保证分布一致
```

**关键优势**：
- Draft 模型快（小模型，低延迟）
- Target 模型并行验证（批处理 k 个 token）
- 无损加速（输出分布与原始模型完全一致）

#### 算法流程

```python
def speculative_decoding(
    draft_model,
    target_model,
    input_ids,
    k=4  # 推测长度
):
    while not finished:
        # 1. Draft 阶段：小模型生成 k 个候选
        draft_tokens = []
        draft_probs = []
        for _ in range(k):
            logits_d = draft_model(input_ids + draft_tokens)
            p_d = softmax(logits_d)
            token = sample(p_d)
            draft_tokens.append(token)
            draft_probs.append(p_d[token])
        
        # 2. Verify 阶段：大模型并行验证
        # 一次前向计算验证所有候选
        logits_t = target_model(input_ids + draft_tokens)
        target_probs = [softmax(logits_t[i]) for i in range(k)]
        
        # 3. Rejection Sampling
        accepted = []
        for i in range(k):
            p_accept = min(1.0, target_probs[i][draft_tokens[i]] / draft_probs[i])
            if random() < p_accept:
                accepted.append(draft_tokens[i])
            else:
                # 拒绝，从修正分布采样
                p_corrected = normalize(max(0, target_probs[i] - draft_probs[i]))
                bonus_token = sample(p_corrected)
                accepted.append(bonus_token)
                break  # 停止验证后续 token
        
        input_ids.extend(accepted)
```

### 3.3 拒绝采样 (Rejection Sampling)

#### 数学原理

**目标**：保证输出分布与 Target Model 完全一致。

**接受概率**：
$$P(\text{accept } x) = \min\left(1, \frac{p_{\text{target}}(x)}{p_{\text{draft}}(x)}\right)$$

**修正分布**（拒绝时采样）：
$$p'(x) = \frac{\max(0, p_{\text{target}}(x) - p_{\text{draft}}(x))}{\sum_{x'} \max(0, p_{\text{target}}(x') - p_{\text{draft}}(x'))}$$

#### 正确性证明

设 $q(x)$ 为 Draft 分布，$p(x)$ 为 Target 分布。

采样过程：
1. 从 $q(x)$ 采样 $x$
2. 以概率 $\alpha(x) = \min(1, p(x)/q(x))$ 接受
3. 若拒绝，从 $r(x) \propto \max(0, p(x) - q(x))$ 采样

**最终分布**：
$$P(X=x) = q(x) \cdot \alpha(x) + (1 - \sum_{x'} q(x')\alpha(x')) \cdot r(x)$$

经过推导可证明 $P(X=x) = p(x)$，即与 Target 分布一致。

### 3.4 性能分析

#### 加速比计算

设：
- $\gamma$: 接受率（平均接受的 token 数 / k）
- $k$: 推测长度
- $r$: Draft 模型速度 / Target 模型速度

**理论加速比**：
$$\text{Speedup} = \frac{1 + \gamma k}{1 + k/r}$$

**特殊情况**：
- 若 Draft 模型极快（$r \to \infty$）：$\text{Speedup} \approx 1 + \gamma k$
- 若接受率为 1（$\gamma = 1$）：$\text{Speedup} = 1 + k$

#### 接受率影响

| 接受率 $\gamma$ | k=4 | k=8 | 说明 |
|----------------|-----|-----|------|
| 0.9 | 4.6x | 8.2x | 高质量 Draft |
| 0.7 | 3.8x | 6.6x | 中等质量 |
| 0.5 | 3.0x | 5.0x | 低质量 |
| 0.3 | 2.2x | 3.4x | 很差 |

**结论**：接受率越高，加速越明显。

### 3.6 树形推测 (Tree Speculation)

#### 动机

线性推测的局限：
```
Draft: [A] → [B] → [C] → [D]
       ↓
如果 A 被拒绝，B/C/D 全部浪费
```

#### 树形推测

生成多分支候选树：
```
        [A]
       /   \
     [B]   [C]
    / \   / \
  [D][E][F][G]
```

**优势**：
- 提高至少一条路径被接受的概率
- 更好地探索可能的延续

**实现**：
```python
def generate_tree(draft_model, input_ids, width=3, depth=4):
    root = TreeNode(token=None, prob=1.0)
    queue = [root]
    
    for level in range(depth):
        new_queue = []
        for node in queue:
            # 生成 width 个子节点
            logits = draft_model(input_ids + node.path)
            top_k_tokens = topk(logits, k=width)
            
            for token, prob in top_k_tokens:
                child = TreeNode(token=token, prob=prob, parent=node)
                node.children.append(child)
                new_queue.append(child)
        
        queue = new_queue
    
    return root
```

## 4. AWQ 量化

### 4.1 背景与动机

#### LLM 部署的挑战

**模型体积问题**：
- LLaMA-7B FP16: 14GB
- LLaMA-13B FP16: 26GB
- LLaMA-70B FP16: 140GB

**限制**：
1. 显存不足：消费级 GPU 无法加载
2. 推理慢：内存带宽瓶颈
3. 成本高：需要昂贵的硬件

#### 传统量化的问题

**均匀量化 (Uniform Quantization)**：
```python
scale = (max(W) - min(W)) / (2^bits - 1)
W_q = round(W / scale)
```

**问题**：
- 忽略权重重要性
- 显著通道量化误差大
- 精度损失严重（>5% perplexity 下降）

### 4.2 AWQ 原理

#### 核心思想

**激活感知 (Activation-Aware)**：通过激活值识别重要权重通道。

**观察**：
1. 少数通道对输出影响大（显著通道）
2. 显著通道对应的权重更重要
3. 保护重要权重可减少量化误差

#### 数学公式

**缩放因子计算**：
$$s_i = \left(\frac{\max|X_i|}{\max_j |X_j|}\right)^\alpha$$

其中：
- $X_i$: 第 $i$ 个通道的激活值
- $\alpha$: 缩放指数（通常 0.5）

**权重缩放**：
$$W'_{ij} = W_{ij} \cdot s_i$$

**量化**：
$$W_{q,ij} = \text{round}\left(\frac{W'_{ij}}{s_{\text{quant}}}\right)$$

**推理时**：
$$Y = (W_q \cdot s_{\text{quant}}) \cdot (X / s)$$

### 4.3 显著通道识别

#### 激活观察

```python
class ActivationObserver:
    def __init__(self, num_features):
        self.running_max = np.zeros(num_features)
        self.n_samples = 0
    
    def observe(self, x):
        # x: [batch, seq_len, num_features]
        batch_max = np.abs(x).max(axis=(0, 1))
        self.running_max = np.maximum(self.running_max, batch_max)
        self.n_samples += x.shape[0]
    
    def get_importance(self):
        return self.running_max
```

#### 显著通道选择

```python
def find_salient_channels(importance, ratio=0.01):
    # 选择 top 1% 的通道
    threshold = np.percentile(importance, 100 * (1 - ratio))
    salient = importance > threshold
    return salient
```

### 4.4 分组量化

#### 动机

全局量化精度不足，分组量化可以更精细：

```
全局: [W_1, W_2, ..., W_n] → 1 个 scale
分组: [W_1...W_g] → scale_1
      [W_{g+1}...W_{2g}] → scale_2
      ...
```

#### 实现

```python
def group_quantize(weight, group_size=128, bits=4):
    out_features, in_features = weight.shape
    n_groups = (in_features + group_size - 1) // group_size
    
    scales = []
    zeros = []
    qweight = []
    
    for g in range(n_groups):
        start = g * group_size
        end = min(start + group_size, in_features)
        w_group = weight[:, start:end]
        
        # 计算量化参数
        w_min = w_group.min(axis=1, keepdims=True)
        w_max = w_group.max(axis=1, keepdims=True)
        
        qmin, qmax = 0, 2**bits - 1
        scale = (w_max - w_min) / (qmax - qmin)
        zero = qmin - w_min / scale
        
        # 量化
        q = np.clip(np.round(w_group / scale + zero), qmin, qmax)
        
        scales.append(scale)
        zeros.append(zero)
        qweight.append(q)
    
    return np.concatenate(qweight, axis=1), scales, zeros
```

### 4.5 INT4 打包

#### 存储优化

INT4 权重可以打包到 INT8 中，节省 50% 内存：

```python
def pack_int4(weights):
    # weights: [N] uint8, 值范围 0-15
    # 返回: [N//2] uint8
    assert weights.max() < 16
    
    packed = np.zeros(len(weights) // 2, dtype=np.uint8)
    packed = weights[::2] | (weights[1::2] << 4)
    
    return packed

def unpack_int4(packed, original_shape):
    # 解包
    low = packed & 0x0F
    high = (packed >> 4) & 0x0F
    
    unpacked = np.empty(len(packed) * 2, dtype=np.uint8)
    unpacked[::2] = low
    unpacked[1::2] = high
    
    return unpacked.reshape(original_shape)
```

### 5.3 性能调优

#### 批大小选择

```python
def optimal_batch_size(
    model_size_gb,
    gpu_memory_gb,
    avg_seq_len,
    block_size=16
):
    # KV Cache 内存估算
    kv_cache_per_token = model_size_gb * 0.1  # 经验值
    kv_cache_per_seq = kv_cache_per_token * avg_seq_len
    
    # 预留模型权重和激活内存
    available_memory = gpu_memory_gb - model_size_gb - 2
    
    # 计算最大批大小
    max_batch = int(available_memory / kv_cache_per_seq)
    
    return max_batch
```
